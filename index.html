Building a Simple 3D Renderer in Java Swing

Understanding the fundamentals of 3D graphics through software rendering.

Introduction

Most modern applications use graphics APIs such as OpenGL, DirectX, or Vulkan to render 3D objects. I wanted to understand what happens behind those APIs, so I built a small 3D renderer using only Java Swing and basic mathematics.

The goal was simple:

  • Display a 3D object (Tetrahedron)
  • Rotate it using sliders

By the end of the project I had a software renderer capable of drawing and rotating a tetrahedron completely on the CPU.

The Object

The renderer uses a tetrahedron made of four triangles (faces).

Each triangle consists of three vertices:

new Vertex(x, y, z)

Representing the model as triangles mirrors how modern graphics hardware works internally.

Rotating the Object

To rotate the tetrahedron I used rotation matrices.

Rendering the Wireframe

The first version of the renderer ignored the z-coordinate completely.

Using Java's Graphics2D and Path2D classes, each triangle edge was drawn as a line.

This produced an orthographic wireframe view of the tetrahedron.



Although simple, this step verified that the matrix transformations were working correctly.

Barycentric Coordinates

Barycentric coordinates express a point as a weighted combination of the triangle's vertices.

  • b1
  • b2
  • b3

These values describe how much influence each vertex has on a pixel.

Besides determining triangle membership, barycentric coordinates can also interpolate values across a surface.

Implementing a Z-Buffer

After rasterization, another problem appeared.

Triangles were rendered in the order they were stored. This meant a triangle behind another could incorrectly appear in front.

To solve this, I implemented a z-buffer.

See how the last face to be rendered appears in front:

The z-buffer stores the closest depth value for every pixel on the screen.
  1. Interpolate depth using barycentric coordinates
  2. Compare depth against the z-buffer
  3. Draw the pixel only if it is closer
  4. Update the z-buffer

Challenges

  • The rasterized image appeared offset from the wireframe due to coordinate translation issues.
  • The z-buffer was initially recreated for every pixel instead of every frame.
  • Depth testing was performed outside the triangle bounds.
  • Determining whether larger or smaller z-values represented pixels closer to the camera required debugging.

Each bug provided a better understanding of how real rendering pipelines work.

What I Learned

  • Matrix multiplication
  • 3D rotations
  • Coordinate transformations
  • Barycentric coordinates
  • Triangle rasterization
  • Depth buffering
  • The fundamentals of the graphics pipeline

Conclusion

Building a renderer from scratch was a very interesting experience. I have previously used graphics APIs(OpenGl), but implementing the entire pipeline manually provided a much deeper understanding of how 3D graphics work.
